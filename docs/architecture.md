# 知識体系・データ設計

## 1. 基本方針

Math-OS は、科目ごとの章立てを唯一の知識構造としない。中心となるのは概念ノードと、概念間の型付き関係からなるネットワークである。

教科書の単元順は学習経路として重要なので保持するが、数学的な依存関係・発展関係とは別の情報として管理する。

## 2. 3つの見方

### 2.1 学校カリキュラムマップ

数学I・A・II・B・III・Cなど、学校教育課程・教科書との対応を示す。科目タグは概念に付与するメタデータであり、概念の本質的な所属を一つに固定するものではない。

### 2.2 概念ネットワーク

前提・技能・一般化・表現変換・応用など、概念間の関係を表示する。学習者は「次に何を学ぶか」だけでなく、「なぜそれが前提なのか」「何に発展するか」をたどれる。

### 2.3 数学的テーママップ

科目横断で数学を眺めるための分類。初期案として次の領域を設ける。

- 数学的な言語・論理
- 数・代数・式
- 関数・対応・表現
- 図形・空間
- 離散数学・数え上げ
- 変化・極限・解析
- 確率・統計・データ

これは排他的な分類ではない。概念は複数の領域に関係し、領域自体も改訂可能とする。モデリング、表現、近似、一般化、変換などは横断テーマとして扱う。

## 3. 関係の種類

概念間のエッジには必ず関係型を持たせる。

| 関係型 | 意味 |
|---|---|
| prerequisite | 概念理解の数学的前提 |
| skill_dependency | 操作・技能上の前提 |
| generalization | 一般化・拡張 |
| application | 応用・利用 |
| representation | 表現の変換・対応 |
| conceptual_link | 共通構造や重要な関連 |

「数学的に前提であること」と「学校で先に教わること」は別である。学校での配列はカリキュラムマップ側に記録する。

## 4. 概念ノードの推奨スキーマ

初期データでは、概念ごとに次の情報を持つ。

- `id`: 変更されにくい一意識別子
- `title`: 表示名
- `summary`: 短い説明
- `course_tags`: 対応する科目タグ
- `theme_tags`: 数学的テーマ
- `prerequisites`: 必要な概念ID
- `relations`: 型付き関係
- `content_path`: 本文ファイルの場所
- `status`: draft / reviewed / published
- `sources`: 参照資料と該当箇所
- `last_reviewed`: 最終確認日

本文と機械可読データを分離し、本文の改稿が概念IDや関係IDを不必要に変えないようにする。

## 5. 学習経路

一つの固定ルートを唯一の正解にしない。学習者の既習状況・目的に応じて複数の経路を生成できるよう、前提関係とカリキュラム順を分離する。

ただし、前提を飛ばしてもよいという意味ではない。経路上で未習の前提がある場合は、その概念への補助リンクを提示する。

## 6. 初期ディレクトリ案

```text
/
├── README.md
├── docs/
│   ├── vision.md
│   ├── content-standard.md
│   ├── architecture.md
│   └── curriculum-map.md
├── content/
│   ├── math-1/
│   ├── math-a/
│   ├── math-2/
│   ├── math-b/
│   ├── math-3/
│   └── math-c/
├── data/
│   ├── concepts/
│   └── relations/
├── app/
└── tests/
```

初期段階では `app/` を急いで実装しない。まず知識構造・内容基準・実際の単元コンテンツを検証し、構造が安定してからUIとデータ形式を実装する。

## 7. 変更管理

- 概念の追加・統合・分割ではIDの参照整合性を確認する。
- 関係を変更した場合、影響する学習経路を確認する。
- カリキュラム改訂に伴うタグ変更と、数学的な概念変更を区別する。
- 大きな設計変更は `docs/decisions/` に判断理由を残す。
